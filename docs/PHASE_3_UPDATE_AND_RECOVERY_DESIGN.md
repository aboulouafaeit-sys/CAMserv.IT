## 1. Executive Summary & Design Scope

Surveillance appliances installed in remote or critical installations must receive firmware, software, and security updates over-the-air (OTA) without requiring physical on-site service calls. However, an unverified or corrupted update poses catastrophic operational risks: physical bricking, service outage, loss of evidence, or adversary supply-chain compromise.

**Stage 7** specifies and implements a high-assurance, cryptographically signed update engine, release authority signature verification, staged deployment channels, version compatibility checks, and automated atomic rollback.

### Core Lifecycle Invariants:
1. **Mandatory Cryptographic Release Signatures:** Every update bundle must be signed with an **Ed25519 digital signature** generated by the official CAMserv Release Authority. **Unsigned or untrusted packages are rejected at the staging boundary.**
2. **Payload Item Checksum Verification:** Every file in the update archive is independently validated against its declared SHA-256 hash prior to disk extraction. Tampering triggers `PackageIntegrityError`.
3. **Staged Deployment Channels:** Appliances adhere to deployment channels (`stable`, `testing`, `development`). Production appliances reject testing builds unless explicitly reconfigured.
4. **Atomic Rollback Guarantee:** Before extracting any update, the active application state is snapshotted. If post-update service health checks fail, the system automatically rolls back to the prior working state.

## 2. Cryptographically Signed Update Bundle Specification

Implemented in `src/camserv/deploy/updater.py`:

```
+─────────────────────────────────────────────────────────────────────────────────+
|                  CAMserv Update Bundle (*.camserv-upd / *.zip)                  |
+─────────────────────────────────────────────────────────────────────────────────+
| 1. manifest.json                                                                |
|    - package_id: "upd-2026-310"                                                 |
|    - target_version: "3.1.0"                                                    |
|    - minimum_supported_version: "3.0.0"                                         |
|    - channel: "stable"                                                          |
|    - files: [{"path": "bin/app.py", "sha256": "...", "size": 1024}]            |
|    - signature_hex: "d4f8... (64-byte Ed25519 signature)"                       |
+─────────────────────────────────────────────────────────────────────────────────+
| 2. payload/                                                                     |
|    - payload/bin/app.py                                                         |
|    - payload/config/settings.yaml                                               |
+─────────────────────────────────────────────────────────────────────────────────+
```

### Canonical Signing Construction:
$$\text{files\_hash} = \text{SHA256}(\text{json.dumps}(files, \text{sort\_keys}=\text{True}))$$
$$\text{canonical\_bytes} = \text{UPDATE\_V1} \parallel \text{pkg\_id} \parallel \text{target\_ver} \parallel \text{min\_ver} \parallel \text{channel} \parallel \text{ts} \parallel \text{files\_hash}$$
$$\sigma = \text{Sign}_{SK_{\text{Release}}}(\text{canonical\_bytes})$$

## 3. Four-Stage Verification Pipeline

```
[Update Package Downloaded]
            │
            ▼ Stage 1: Manifest Extraction & Channel Check
    (Channel Mismatch?) ──────────► [REJECTED (Channel Incompatible)]
            │
            ▼ Stage 2: SemVer Compatibility Check
    (Current Version < Min?) ─────► [REJECTED (VersionIncompatibilityError)]
            │
            ▼ Stage 3: Release Authority Signature Verification
    (Signature Invalid / Untrusted?) ──► [CRITICAL REJECTION (UpdateSignatureError)]
            │
            ▼ Stage 4: Per-File SHA-256 Checksum Validation
    (Hash Mismatch?) ─────────────► [REJECTED (PackageIntegrityError)]
            │
            ▼
    [APPROVED & STAGED FOR MAINTENANCE WINDOW]
```

## 4. Atomic Rollback & Recovery Execution

Managed by `apply_update_with_atomic_rollback`:
1. **Pre-Update Atomic Snapshot:** Before writing any new file, existing application binaries and configurations are copied to `/data/backup/snapshot_<timestamp>`.
2. **Atomic Extraction:** Payload files are unpacked into target production directories.
3. **Automated Health Probe:** System initiates post-update service health checks (verifying `camserv-core` returns `HTTP 200 OK` on `/api/v1/health` and video decoding threads report nominal FPS).
4. **Automated Rollback on Failure:** If health probes fail within $120\text{s}$, the installer restores the pre-update snapshot, logs an audit alert, and reboots into the safe verified state.

---

## 5. Maintenance Windows & Staged Rollout

To prevent operational disruptions in 24/7 security control rooms:
* **Scheduled Maintenance Window:** Updates are held in a staged state and executed during pre-configured quiet windows (e.g. 02:00 – 04:00 local time).
* **Operator Approval Gate:** High-assurance sites require explicit operator sign-off before applying updates.
* **Canary Fleet Rollout:** When orchestrating fleet-wide updates from CAMserv Central, releases are deployed to 5% of nodes (Canary), monitored for 24 hours, and progressively expanded to 25%, 50%, and 100%.
